# Run statistics: census fourth pass

Generated by `exp/run_translate/stats_report.py`; numbers come from `summary.json` under results/ and `stats/*.json` under the runs directory.

## 1. How the runs are organised

- Host: `chao-srv1.ece.gatech.edu`, 64 CPUs, 502.5 GB; every tool runs in a container of the `hlsfactory-agent` image, the vendor installs bind-mounted read-only.
- Repositories run in 3 concurrent lanes (`run_repo.py`, one process per repo; a lane runs its repos one after another), so the resource columns describe the host while several repos ran, not one repo. Inside a repo, `--jobs 11` designs run concurrently (joblib workers); each design is sequential: oracle, pre-pass, up to `--attempts 3` agent attempts each followed by the static and container checks, then Vitis on the source and catapult on the translation (2400 s budget), then up to 4 recovery rounds.
- A design therefore holds at most one agent container and one tool container at a time; the host sees at most `jobs` x lanes of each. The resource columns below are host-wide samples every 30 s (1-minute load, memory in use, running containers of the image).
- Retry mechanics: after a failed attempt the agent gets the original prompt plus a `Previous attempt failed` section listing the harness's findings (static-check failures, fenced edits with the pre-pass version to restore, compile errors, the testbench diff); the next attempt edits the same output folder. A design passes when the static checks and the container testbench both pass; the retry loop stops at the first pass.
- Stage time is wall time inside the design's worker, so `translate` includes the agent's own wall time and the checks; the per-attempt split (`agent_s`, `check_s`) is in each row's `attempts` list.
