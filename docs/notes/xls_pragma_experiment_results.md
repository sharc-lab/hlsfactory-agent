# XLS[cc] Pragma Experiment Results

Everything here was checked by compiling and running code with our own XLS build. The pragma-by-pragma mapping tables are in [xls_pragma_notes.md](xls_pragma_notes.md); those come from reading the XLS repo and the Vitis docs, so where the two disagree, trust this file. Last updated 2026-10-22.

## Purpose

The notes map Vitis pragmas onto XLS[cc] features by reading source and docs. The experiments check those mappings by writing small XLS C++ programs, pushing them through the XLS toolchain, and looking at what comes out. Each experiment asks one question, such as "does this pragma change the IR, and does the change survive into Verilog?". Priority order: `stream`, `pipeline`, `array_partition`, then everything rated ⚠️ or ❓ in the notes.

## How to run an experiment

Runner: [run.sh](../../exp/xls_pragma_probe/run.sh). It runs `xlscc` then `opt_main` and stops at the optimized IR; Verilog is generated by hand with `codegen_main`.

```sh
cd exp/xls_pragma_probe
./run.sh probes/stream_depth.cc --block_from_class Block      # C++ -> IR -> optimized IR
cd out/stream_depth
codegen_main stream_depth.opt.ir --generator=pipeline --pipeline_stages=2 \
  --delay_model=unit --module_name=Block --reset=rst > stream_depth.v
# add --materialize_internal_fifos to get a self-contained file (stream_depth.mat.v)
```

## Setup facts

- The XLS release tarball (`xls-release/xls-v0.0.0-10753-g4d95f4c94-linux-x64/`, on PATH) has **no `xlscc`**. We built `xlscc` from source (checkout `e735697f0`, 2026-09-29) at `/export/hdd/scratch/jzhou652/xls/bazel-bin/xls/contrib/xlscc/xlscc`, symlinked as `~/bin/xlscc`. The other tools are the older release build; mixing them worked in our tests, but if IR errors show up, suspect the version difference first.
- No `yosys`, `sta`, `iverilog` or `openroad` on PATH on `chao-srv1`, so there are no area or timing numbers yet.
- **Channels need block mode.** A program with `__xls_channel` must be run with `--block_from_class <Class>` (plus `--block_pb <out file>`, which is an output in this mode; `run.sh` adds it). Without it xlscc emits a plain function with I/O-op parameters, and `opt_main` rejects it ("channel has no associated send node").

## Experiment 1: `hls_fifo_depth` on an internal channel

**Files:** [probes/stream_depth.cc](../../exp/xls_pragma_probe/probes/stream_depth.cc) → [out/stream_depth/](../../exp/xls_pragma_probe/out/stream_depth/) (`stream_depth.ir`, `stream_depth.opt.ir`, `stream_depth.v`, `stream_depth.mat.v`). Pragma row in the notes: [`hls_fifo_depth`](xls_pragma_notes.md).

**Question:** is `[[hls_fifo_depth(N)]]` a real FIFO-depth control, the way `#pragma HLS stream depth=N` is in Vitis, or just metadata? **Result:** ✅ it reaches the IR and the Verilog.

**Context:** An XLS *channel* (`__xls_channel<T>`) is like `hls::stream<T>`: typed, ordered, ready/valid. A channel declared as a direction-tagged class member (`..._dir_In`/`..._dir_Out`) is an *external* channel and becomes module ports. A `static __xls_channel<T>` declared inside the method is an *internal* channel with both ends in the same block. A channel is an abstraction; a FIFO is one way to buffer it. This experiment sets the depth explicitly, so it does not tell us what an internal channel gets by default.

**C++ (`probes/stream_depth.cc`, the whole program)**
```cpp
class Block {
  __xls_channel<int, __xls_channel_dir_In>  in;    // external: becomes ports
  __xls_channel<int, __xls_channel_dir_Out> out;   // external: becomes ports

  #pragma hls_top
  void foo() {
    [[hls_fifo_depth(4)]]
    static __xls_channel<int> internal;            // internal: depth set here

    const int x = in.read();
    internal.write(x * 2);
    const int xr = internal.read();
    out.write(xr);
  }
};
```

**IR (`out/stream_depth/stream_depth.opt.ir`).** The external channels have no depth field; the internal one does.
```
chan in(bits[32], ..., kind=streaming, ops=receive_only, flow_control=ready_valid, ...)
chan out(bits[32], ..., kind=streaming, ops=send_only, flow_control=ready_valid, ...)
chan __internal_foo_internal(bits[32], ..., ops=send_receive, flow_control=ready_valid,
     fifo_depth=4, bypass=true, register_push_outputs=false, register_pop_outputs=false)
```

**Verilog (`out/stream_depth/stream_depth.v`).** External channels become ready/valid ports; the internal channel becomes a FIFO instance with `Depth(4)`.
```verilog
module Block(
  input  wire clk, input wire rst,
  input  wire [31:0] in,  input wire in_vld,  output wire in_rdy,
  output wire [31:0] out, output wire out_vld, input  wire out_rdy
);
  ...
  xls_fifo_wrapper #(
    .Width(32'd32), .Depth(32'd4),
    .EnableBypass(1'd1), .RegisterPushOutputs(1'd0), .RegisterPopOutputs(1'd0)
  ) fifo___internal_foo_internal (
    .clk(clk), .rst(rst),
    .push_data(...), .push_valid(...), .push_ready(...),
    .pop_data(...),  .pop_valid(...),  .pop_ready(...)
  );
```

**Findings**
- Width comes from the channel type (`int` gives 32). Depth is a count of values, so 4 slots of 32 bits.
- **`xls_fifo_wrapper` is instantiated but not defined** in `stream_depth.v`. Supply that module or pass `--materialize_internal_fifos`, which emits a self-contained module (`fifo_for_depth_4_ty_bits_32__with_bypass`, in `stream_depth.mat.v`). The synth driver needs one of these.
- The block's Verilog is about 170 lines against about 10 for the FIFO instantiation. The rest is port handshakes, boundary flops, the ordering FSM (`__fsm_foo_impl_state_0`, from `split_states_on_channel_ops`), and the 2 pipeline stages.
- The program has one value in flight at a time and `bypass=true`, so it shows the depth reaches hardware but not that depth changes behavior.
- `bypass`, `register_push_outputs` and `register_pop_outputs` are the nearest XLS knobs to Vitis's `type=` choices; whether C++ can set them is untested.
